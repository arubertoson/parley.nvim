Design questions deferred until after the native review interaction prototype:
- What identifies a review, its baseline, and each piece as code changes?
- How are code anchors, captured context, review progress, and human/agent threads persisted?
- How are targets relocated, and stale/deleted targets presented?
- How are pieces and notes presented to the existing Pi conversation?
- What should export include: selected/all pieces, snapshots, code context, and readable bundles?
- Does exporting or sending change review state? Keep that explicit.
- How does a receiver target the actual conversation, distinguish receipt from processing, and route replies to the right piece?

Priority: establish the native review interaction first. Save/reopen and a receiver round trip are not prerequisites for the first UX experiment.

Later connected-review direction: use context from the existing interactive Pi conversation, not an independently launched agent. Existing runtime tracking lacks conversation/session ID and a runtime can switch conversations. `agent-ack` records completion visitation, not receipt of review feedback. A Pi receiver extension using `pi.sendUserMessage()` is a candidate; its void return does not prove queueing or processing. No transport is selected; bracketed paste without Enter is only a possible confirmation fallback.

Explicitly out of scope for the initial prototype: persistence/schema, export, receiver or transport, agent targeting/delivery/reply routing, new plugin/Hunk daemon/dependency overhaul, broad psst/Tracks refactoring, dashboard or replacement views.
